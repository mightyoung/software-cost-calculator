# 本地优先供应商与询价管理系统设计

版本：1.0 定稿。十项业务选择及完整设计已由用户确认，用户明确回复“确认，按此定稿并编写开发计划”。本文件描述待开发系统，不代表功能已实现。旧 `.omx` 规划与阶段0证据原样保留，新开发以本设计为基线。

## 1. 产品目标与确认范围

在本机录入供应商、联系人、产品和已取得价格的报价，按项目、产品、品牌、型号、供应商、价格、询价日期及询价人聚合查询。通过业务 Excel 编辑回流和专用全量同步包交换数据，避免重复导入、旧文件覆盖新值及并发修改丢失。

| 项目 | 已确认要求 |
|---|---|
| 首版平台 | Windows、Android、Web；iPhone 后续支持 |
| 数据位置 | 本地优先，无业务服务器、账户、权限或登录 |
| 编辑拓扑 | 每端可独立编辑，同一记录并发修改保留分支并人工解决 |
| 业务组织 | 每条报价独立保存项目和询价信息，不建立项目/询价单主表 |
| 规模 | 三年1万—10万条报价；历史修订另计 |
| 普通Excel | 可导出后修改，经预览选择纠正原记录或新增一次询价 |
| 同步 | 首版全量历史，ZIP内含多个Excel分卷；全部验证后一次业务提交 |
| 报价状态 | 只记录已取得价格的报价，不做待回复/不报价流程 |
| 日常新建 | 项目名称/编号至少一项、询价时间、询价人必填；地点选填 |
| 历史导入 | 用户显式选择历史资料模式后可缺上下文字段，保留缺失标记 |
| 询价时间 | 支持仅日期和具体时刻；未知时间不能补造为00:00 |

不包括订单、库存、付款、审批、自动网络同步、附件同步、自动汇率换算、公式计算和增量同步基线管理。文件校验、容量检查、事务、备份与恢复属于稳定性设计。

## 2. 三视角综合与主要决策

**ECC：** 使用本地应用服务、仓储、事务及结构化错误，避免引入不需要的HTTP、Redis和授权层。应用服务拥有事务，所有业务修改通过唯一的修订提交入口，不能让当前行和历史图分别写入。

**Superpowers：** 按可使用的闭环交付，不把纯内核完成当成产品完成。平台能力验证提前进行；先本地工作版，再多端交换版，最后完成首版三端验收。当前Flutter方向有小样依据，但原生集成仍须验证。

**grill-me：** 用户回答排除了单主设备、询价单主表、未报价状态及首发iOS；确认了10万规模、历史例外和日期精度。这些答案优先于旧规划中的推断。

保留完整因果修订图：其复杂度由已确认的多端自由编辑和人工冲突需求支撑。放弃“整个库必须装进单个20MiB工作簿”的限制；本地数据库、单卷、整包和解析工作集分别管理。仅当前值快照不能代替完整历史同步。

## 3. 领域模型

### 3.1 实体与标识

四类实体 Supplier、Contact、Product、Quotation 均使用离线生成的小写UUID v4。姓名、项目编号、品牌型号和电话号码都不是身份键。同ID不同根内容是碰撞，拒绝覆盖；不同ID的相似内容只进入候选列表。

| 实体 | 字段与约束 |
|---|---|
| Supplier | id；name必填≤200字符；aliases最多20项、各≤200；address≤500；categories最多20项、各≤100；notes≤2000 |
| Contact | id、supplier_id、name≤200必填；phone≤100、wechat≤100、email≤254至少一项；notes≤2000 |
| Product | id、name≤200、unit≤50必填；brand/model各≤200、specification≤1000、category≤100、notes≤2000可空 |
| Quotation基础 | id、supplier_id、product_id、price、currency、tax_mode、unit_snapshot、min_qty必填；quoted_on、contact_id、contact_snapshot、tax_rate、lead_time_days、valid_until、notes按下述规则 |
| Quotation上下文 | project_name≤200、project_number≤100、inquiry_location≤500、inquirer_name≤200；inquiry_precision、inquiry_date、inquired_at、inquiry_utc_offset_minutes；capture_mode |

字符长度按Unicode码点计算，Excel另检查UTF-16单元格上限。字符串NFC、去首尾空白，保留内部文字和型号标点；拒绝孤立代理项与非法XML字符。可空文本规范为空值；数组去重并按码点排序。电话和编号始终文本，保留前导零。

### 3.2 金额、联系人与日期

- price非负十进制文本，最多12位整数、6位小数；min_qty为相同精度的正数，默认1。零价格是已取得的零报价，不能代表未知。禁止二进制浮点持久化和比较，使用补齐12+6位的price_key索引。
- currency为三位大写代码，默认CNY。tax_mode为included/excluded/unknown，默认unknown。tax_rate可空，范围0—100、最多4位小数。unit_snapshot保存报价当时单位。
- 选择联系人时校验其供应商，复制姓名及联系方式为contact_snapshot；历史快照不随联系人编辑变化。允许不绑定Contact实体而直接填写完整联系人快照。
- quoted_on是报价业务日期，与询价时间独立；标准新建必填。历史资料确实缺报价日期时允许null并列入缺失项，不自动使用今天或询价日期。valid_until有值时必须有quoted_on且不早于它；否则要求补日期或清除无依据的有效期。lead_time_days为0—36500或null。

### 3.3 日期精度契约

| inquiry_precision | 必须有值 | 必须为null | 语义 |
|---|---|---|---|
| date | inquiry_date=`YYYY-MM-DD` | inquired_at、inquiry_utc_offset_minutes | 只知道当地日历日期，不表示某个UTC瞬间 |
| instant | inquiry_date、inquired_at、inquiry_utc_offset_minutes | 无 | UTC毫秒时刻+原偏移；inquiry_date必须等于按偏移还原后的本地日期 |
| unknown | 无 | inquiry_date、inquired_at、inquiry_utc_offset_minutes | 仅显式历史资料模式允许，表示日期也未知 |

具体时刻规范为`YYYY-MM-DDTHH:mm:ss.SSSZ`与-840至840分钟偏移；输入接受带Z/偏移的有效时间，0—3位小数秒，禁止非法日期、闰秒和精度截断。输入只有日期就使用date，不补00:00。界面选择日期/具体时刻，隐藏序列化格式细节；无秒输入按该分钟起点记录，并在预览显示最终值。

按“询价日期”筛选使用保存的inquiry_date，不因查看设备时区改变。date与instant同日属于同一日期组；date不得在日内排序时被当成00:00，日内时间未知单独显示。unknown可筛选“日期缺失”。

### 3.4 标准记录与历史例外

capture_mode固定为standard或historical，由创建流程明确写入并参与修订与同步。standard必须有项目名称/编号至少一项、非unknown询价时间、询价人、quoted_on及全部基础字段。历史导入仍必须有可匹配的供应商、产品和已知价格；仅允许项目、询价人、询价日期、报价日期等上下文缺失。

缺失项从当前内容派生，不作为额外权威字段同步。historical允许纠错而不强迫补造其他未知信息；清空已有信息须显式确认。补齐后可执行“转为标准记录”，创建新修订。复制为新询价必须按standard重新校验，不能继承历史例外。普通编辑不能把standard降为historical以绕过必填。

旧阶段0快照仅可通过专用迁移入口生成新协议根修订：有时刻则转instant，缺时间则unknown，capture_mode为historical，保留已有实体ID及关系。迁移到空业务库，按源逻辑摘要登记一次性回执；不得伪造其拥有正式v1历史。

## 4. 本地架构与一致性

架构：响应式Flutter界面 → 应用服务 → 纯Dart领域规则/仓储接口 → Drift/SQLite及平台文件适配。

- RecordService：新增、纠错、复制、删除、恢复、实体合并、冲突解决。
- ExchangeService：业务Excel导入导出、全量分卷同步、预览、提交和任务恢复。
- BackupService：一致备份、验证临时库、切换活动库、恢复后检查。
- QueryRepository：投影查询、分页、候选筛重、聚合统计；不逐行发起关联查询。

权威表：entity_identity、revision、revision_parent。派生表：entity_head、supplier/contact/product/quotation_projection、reference_projection、alias_projection。本地辅助表：database_meta(generation)、import_batch、staging_revision、staging_row、import_row_receipt、local_settings。暂存表必须与业务查询隔离。

单次业务修改在一个事务内校验预期heads和generation、插入修订、更新受影响投影、递增generation、记录成功回执。每个写连接启用并验证foreign_keys，提交前校验新增关系。迁移DDL与schema版本同事务，迁移前备份、失败保持原库。SQLite支持单写事务；应用也实施单写者协调。[SQLite事务说明](https://www.sqlite.org/lang_transaction.html)、[Drift事务说明](https://drift.simonbinder.eu/dart_api/transactions/)

原生使用独立数据库工作线程；Web使用WASM worker及经过验收的持久后端。内存或unsafeIndexedDb禁用业务写入；无法获得可靠应用写锁时第二标签只读。部署固定WASM/worker版本与MIME，选用要求隔离头的后端时按部署契约配置。浏览器持久存储请求结果可见，但不能承诺不会被清理。[Drift Web说明](https://drift.simonbinder.eu/platforms/web/)

## 5. 正式同步协议：分卷全量交换

### 5.1 版本与包结构

新格式：`supplier-inquiry-bundle`，bundle_version=1，schema_version=2，修订envelope中protocol=2。这三种版本分别描述容器、领域字段和修订编码，不复用阶段0格式。旧规划v1及golden仅作不可改写的历史证据；首版不宣称支持未发布的混合v1/v2历史。未来升级必须提供独立迁移规范与fixtures。

文件名建议`供应商询价-日期-包ID.siq.zip`。外层ZIP使用STORE保存已经压缩的xlsx分卷，包含`manifest.json`、`revisions-000001.xlsx`等修订卷及`suppliers/contacts/products/quotations-000001.xlsx`等业务投影卷。分卷序号只是包内顺序，不是业务身份。

manifest固定字段：format、bundle_version、schema_version、bundle_id、exported_at、exporter_version、revision_count、entity_counts、revisions_digest、business_digest、volumes。每卷条目含path、kind、index、row_count、sha256、compressed_bytes、expanded_bytes。文件集合必须与manifest精确相等；拒绝缺卷、多卷、重复路径、绝对路径及目录穿越。hash用于识别损坏，不是认证。

修订卷固定列revision_id、entity_type、entity_id、envelope_json。业务卷按实体ID升序输出可读投影，表头固定且业务标量文本、空值为空白。跨卷不能重复修订或投影行。manifest中的逻辑摘要独立于压缩方式，卷sha256则精确绑定实际分卷字节；手动重存分卷导致字节变化时不能当原同步包接受。需要编辑时使用业务Excel导出入口。

全局revisions_digest为按revision_id升序逐行连接`revision_id + TAB + canonical_envelope + LF`的UTF-8 SHA256；canonical_envelope中不含原始制表或换行。business_digest为固定实体类型顺序、每类型先一行JCS表头、再按entity_id排序的JCS字符串数组行，每行LF的SHA256。空表仍计表头。这是新格式规则，不沿用旧v1摘要定义。精确字段表和示例由协议任务生成schema及golden后锁定，禁止各端自由推断。

所有分卷、计数、逻辑摘要和业务投影必须来自同一个一致读快照。导出先固定快照，将输出写入任务临时目标；允许另建经验证的快照库以释放活动库的长期读锁，但不能在分卷之间重新读取活动库。完成所有分卷及manifest后重新验证整包，最后才公布可下载/保存结果。导出期间的并发修改留到下一包；取消、中断或空间不足不得把部分ZIP作为成功包交付。残留任务文件可清理或在同一快照仍可用时重试，不续接另一个版本的数据。

### 5.2 因果、冲突与删除

revision_id为RFC8785 JCS envelope的SHA256。envelope字段：protocol、entity_type、entity_id、parents、kind、payload、authored_at、origin_device_id。parents排序去重；put是完整快照，delete为空payload，redirect仅target_id。可选字段必须显式null，未知/缺失键拒绝。

每个实体只有一个put根；父修订必须存在且同实体，图无环。包必须包含全部历史、删除标记、冲突分支及关联实体闭包。导入是修订集合并集：相同修订不重复；旧包不能压掉新head；多head保持冲突，不按时间或字段自动胜出。即使并行内容相同，也保留因果，提供一键确认完整版本。人工解决创建继承全部已知heads的新修订；第三端未见的新分支仍会再触发冲突。

删除不物理清历史，不级联删报价；恢复必须显式创建后继。实体合并为目标put及来源redirect的一次事务；原始引用保持，投影解析canonical目标。重定向环/并行重定向标关联异常并阻止该分量参与新录入、比价；提供选择保留实体的显式修复，继承相关全部heads。误合并不直接撤销既有历史，使用明确的恢复与重定向修订修复。

### 5.3 暂存、确认与原子提交

任务状态：created → parsing → validating → preview_ready → committing → committed；可进入cancelled或failed，预览过期转回validating。文件丢失时重新选择并校验源摘要，不能换文件继续同一任务。

逐卷有界解析到持久暂存，可分批提交暂存进度；这些写入不等于业务导入。全卷齐备后验证hash、计数、schema、JCS、图、闭包和投影一致性，生成带generation的预览。按卷完成状态恢复解析；未完成卷先清理该卷暂存后重试。

确认时取得单写锁，检查generation。变化则重算预览，不使用陈旧匹配结果。业务修订、投影、成功批次和回执在同一事务中全部提交；禁止每个卷分别进入业务库。失败日志在回滚后单独保存。提交后崩溃再打开依据数据库committed状态显示结果；重复导入仍按修订集合判断，不仅凭包ID跳过。

解析/预览允许取消；提交中取消在可中断边界触发回滚，若已完成提交则准确显示完成，不宣称撤销。应用退出后不承诺继续执行，只承诺重开可安全重试或恢复。

## 6. 普通 Excel 导入、修改回流与筛重

业务导出使用中文表头，并附记录ID、记录类型、导出时修订ID和导出模板版本作为匹配提示；技术提示不赋予同步因果权威。支持外部无ID表。业务导出包含所有已确认的项目/询价字段、精度及缺失提示。

流程：选择标准/历史资料模式 → 选表/映射 → 格式转换预览 → 逐行校验 → 实体候选匹配 → 选择修改/新询价/跳过/显式排除错误行 → 最终预览 → 原子提交所选子集。错误排除数量与原因必须可见。

供应商名称/别名、联系人归属+姓名+联系方式、产品品牌+型号+规格+单位用于候选，不作唯一键。首次单一候选也确认，可批量操作。已知ID对应deleted/redirect/conflicted时分别走恢复、canonical目标或冲突专用流程，普通导入不能绕过。

选择“修改原记录”时展示本地当前值、来件和导出基线提示；若本地已不同于导出修订，明确提示旧文件并重新确认。选择“新增询价”生成新ID，按standard校验，不覆写旧价格。没有基线也允许人工比较，但不声称自动判断新旧。

本地普通导入使用两级版本化指纹。source_fingerprint对规范来件计算：映射后的业务字段、输入中的记录ID/供应商产品标识文字、原始缺列/空白/有值三态、项目/询价精度、capture_mode和用户显式批次默认值；不含文件名、行号、压缩字节、本地当前值或重新解析的canonical ID。按固定键序编码，对同义映射名统一；修改映射或批次默认值改变其语义时应产生不同指纹。

重导先按source_fingerprint查成功历史回执，再做新的候选匹配。回执保存当时确认的原始身份绑定、字段操作意图、结果ID集合与数量；operation_fingerprint另对“保留/清空/写值”的显式操作图及修改/新询价意图计算，绝不能使用应用后合成的完整记录作来件身份。存在唯一已确认回执时默认显示已导入、跳过；有多份不同选择回执时展示原选择，不再自动新增。用户明确重新处理、修改映射或另一次真实询价时重新预览并登记新选择，不能静默复用旧决定。

因此，本地备注A后来改B、记录被删除、供应商被合并，均不改变旧回执查找身份，也不能使相同旧表恢复旧内容。当前canonical ID只用于显示/执行用户新确认的动作，不能回写原回执键。同内容确为新一次询价时仍可显式新建，保存确认数量。

新建空格表示null；更新空格默认不改，清空必须显式选择。普通表数字金额可在预览中按原始数值词法精确转换，超过精度拒绝，不经过二进制浮点；已被Excel损坏的长编号不能猜回。日期序号按工作簿1900/1904日期系统转换并显示预览，拒绝虚构的1900-02-29；本地日期时间缺时区时要求批次明确偏移，不能默用设备时区。仅日期走date；公式拒绝使用缓存结果，提示转为值。

## 7. 查询、比价与界面

导航为查询与比价、供应商、产品、导入导出/备份；新报价全局可达。Windows/Web桌面提供分页表格、列显隐、详情和批量操作；Android提供搜索列表、分步录入及联系动作。无登录入口，不做无业务价值的仪表盘。

组合筛选包含供应商/联系人、产品名称/品牌/型号、项目名称/编号、询价日期范围/精度/缺失、询价人、报价日期、价格范围、历史缺失状态。结果按稳定排序键分页，默认50条，不载入全部十万条。项目文字保留快照，可按精确值或搜索候选聚合；改项目名称不批量重写历史。

搜索键可做NFKC、大小写折叠、空白合一以找候选，存储原文字仍NFC；型号标点保留。先使用索引支持精确/前缀搜索，包含搜索单独测性能。建立产品/供应商/报价日期、项目编号/询价日期、询价人/询价日期、精确比价口径与price_key等复合索引，以查询计划和真实基准修正，不添加未使用索引。

比价只在同canonical产品、unit_snapshot、currency、tax_mode、min_qty口径内进行；含税还区分tax_rate。未知税制只展示，不参与最低价。报价日期未知/未来、过期、供应商或产品异常、冲突记录不参与“已确认有效最低价”；有效期未知显示待确认。用户可切换查看所有历史，不能隐去这些记录。每供应商最新按quoted_on，同日并列，不用UUID或日期精度不足的询价时间猜先后。

## 8. 容量、备份与平台稳定性

目标基准为10,000与100,000条报价，最大基准另含10,000供应商、20,000产品、20,000联系人、累计500,000修订。它是发布必须通过的代表性数据集，不是无限历史承诺，也不是达到该数就停止所有写入。

初始工程工作集参数：每xlsx卷最多5,000数据行、8MiB压缩、32MiB实际展开，取先触达者；每envelope≤24,000 UTF-16单位、每单元格≤32,767；每卷最多2048 ZIP条目。导出超限自动缩小卷并重试，单条本身超限则整个导出失败且保留库。外层ZIP及摘要流式处理，不把所有卷读入内存。工作集参数要用移动端峰值测量锁定；未通过就缩卷或更换适配器，不能把32MiB展开等同于32MiB内存。

整包不设旧20MiB总上限，也不按包大小禁止单条业务纠错。接收前检查源大小、声明展开总量、暂存、目标库增量、事务日志和备份的预计空间，实际展开持续计数；空间不足在提交前拒绝，提交中的不足必须回滚。空间预测是提前提示，事务正确性不能依赖预测准确。所有读取/导出仍尽可能开放；存储真实耗尽时不能保证可继续写入，提供清理应用暂存、外部备份和迁移库的入口，不自动删历史。

原生采用一致快照机制或逻辑备份，禁止只复制活动WAL库的主文件。备份通过独立完整性校验后才显示完成。[SQLite备份说明](https://www.sqlite.org/backup.html)

跨端逻辑备份格式独立于同步：包含全部修订、设置及本地导入回执，不包含缓存/锁/设备身份；恢复保留本机设备ID。恢复先建立新库、验证图与投影，再切换活动库指针；旧库保留至重开校验成功，切换各中断点均须可恢复。Web以版本化临时库和可原子更新的活动库指针实现相同语义。

非空库批量导入/迁移前生成完整备份。Web只能报告备份生成并已发起下载，不能声称已落到用户磁盘；生成或下载发起发生可观察错误则不提交批量导入。Web离线资源缓存必须版本化，更新不得混用WASM/worker/应用版本；第一次加载需联网，浏览器主动清库且无外部备份时不能恢复。

首版发布矩阵目标：Windows 11 x64、Android 10及以上arm64真机、桌面Chrome/Edge当期稳定版及上一稳定版。具体测试设备、浏览器版本、Flutter/Dart及文件库版本在平台能力任务中记录并锁定；未达到不得宣称支持。iOS不在首版发布门内，但领域核心和文件接口不依赖Android专有行为。

性能目标：规定基准设备并预热后，索引查询首50条20次p95≤500ms；包含搜索首50条p95≤2s；输入到首屏≤1s。交换1s内显示进度，解析取消2s内反馈。标准10万/50万fixture全量导入桌面≤10分钟、Android≤20分钟，应用峰值内存桌面≤1GiB、Android≤512MiB；Web应用worker+页面内存采用浏览器可观测指标并披露测量范围，不能拿进程RSS与原生混比。数值是工程验收目标，测不到或不通过要记录失败并修复，不替换成“体感流畅”。

开发按三条产品里程碑推进：M1本地工作版（录入/查询/业务Excel/备份）；M2多端交换版（全量分卷/筛重/冲突/恢复）；M3首版三端发布（实际安装、生命周期、软件往返、规模和故障矩阵）。正式修订仓储必须在M1使用，不能先做可变CRUD再另造同步历史。平台工具链与领域规则可并行，协议和公共接口冻结后才拆分文件适配/UI任务。
