# AI 连续性、缓存与上下文压缩

## 本轮修改计划（修改代码前记录）

1. 用回归测试锁定：合法多段导入及 JSON 修复重试不能被固定 24 次限制截断；未显式配置总截止时间的任务，不因累计耗时而中断。
2. 有限工作流按已知工作量配置调用上限（每个步骤含一次 JSON 修复重试）；保留调用级超时、主动取消及显式配置的总截止时间。对话保留防循环边界及最终总结轮。
3. 不引入新依赖、Redis 服务、语义答案缓存或未经验证的摘要。研究完整 compact 和恢复方案，明确当前尚未实现的部分。
4. 运行核心回归、静态分析与相关界面回归；网络模型已在前轮验证，本轮控制流故障使用可重复的模拟响应验证。

## 结论与本轮交付边界

**目前不接 Redis；需要自动上下文管理，但必须同时设计原文回查和任务断点。** 本轮已经修正固定预算对正常工作流的误伤，未把下文建议中的缓存、持久化任务、语义摘要当成已实现功能。当前还不能承诺长对话永不中断。

缓存解决重复计算；compact 解决模型输入装不下；持久化检查点解决中断后从哪里继续。这是三个不同问题，安装 Redis 不能一并解决。目标应是：正常有限任务可以完成，异常任务可以停止，失败后不必重做已完成工作，而不是无限放开模型调用。

## 代码核查与实际修正

| 问题 | 原行为及影响 | 本轮状态 |
|---|---|---|
| 正常批量任务超过固定次数 | 清单允许200项，15项一批匹配。一次提取加14批匹配，若每步需一次JSON修复，共30次，超过24次固定上限 | 已修：提取按实际分段数，清单按分段数加最多14个匹配步骤，每步预留2次；不按模型自行提出的“计划”扩额 |
| 累计时间误伤 | 每个请求都在正常返回，整个任务仍可能超过3分钟而失败 | 已修：默认无累计截止时间；每次模型调用独立使用配置的请求超时，默认120秒。调用方明确指定总截止时间时仍执行 |
| 自主对话循环 | 8轮工具后已有最后一次无工具总结；单轮突然申请过多工具仍会报错 | 保留现有8轮/24工具边界；工具批次超限尚未改成可恢复暂停 |
| 历史被静默丢弃 | `assistant.dart` 只带最近6轮、最多12000字符；最近一轮本身过长时可能一轮也不带 | 待改：滚动记忆及原文回查；不能把直接删历史称作compact |
| 当前查询上下文过大 | 消息超过64000字符直接异常，已查到的结果不能保证形成最后回答 | 待改：在阈值前整理上下文并保留取回路径 |
| 同页追问不连续 | `ask_page.dart` 的历史开关默认关闭，也影响当前页面刚产生的问答 | 待产品调整：清楚区分“继续当前会话”和“引用保存的旧会话”；本轮保留现有不自动上传历史的承诺 |
| 失败后从头重做 | 导入结果只在内存累积，失败后没有分段检查点；问答只保存最多100条界面消息，证据不持久化 | 待改：这是连续性优先级最高的后续工作之一 |

主要实现位置：[运行层](../../packages/supplier_core/lib/src/ai_runtime.dart)、[模型客户端](../../packages/supplier_core/lib/src/llm.dart)、[报价提取](../../packages/supplier_core/lib/src/material_import.dart)、[清单匹配](../../packages/supplier_core/lib/src/list_import.dart)、[对话](../../packages/supplier_core/lib/src/assistant.dart)。现有调用者注入的更严格 `AiRun` 限制不会被静默扩大；显式对话截止时间在复用既有run时也有效。

请求大小、最多6万字符输入、最多200条草稿等限制仍然存在；输出被模型长度限制截断时仍然报错，不能把残缺JSON当成功。请求超时也仍可能中断慢模型。此次修正解决的是固定总预算缺陷，不是网络、提供商配额、输出上限和进程退出的所有中断。

## Redis 8 的“AI支持”是什么

Redis 8发布时把JSON、查询等能力统一进开源发行版，并引入向量集合（发布时为beta）来存储、检索向量；向量检索有助于语义搜索和推荐。这不等于自带能理解本项目业务的模型或自动会话管理器。这里只说明8.0发布时的能力，未把当时beta状态当作所有后续版本的当前状态。[Redis 8 官方发布说明](https://redis.io/blog/redis-8-ga/)

Redis的语义缓存按语义相似度复用以前生成的答案，和RAG检索原文是不同用途。其官方文档也指出，相似度阈值过宽会返回错误答案，过严则命中率很低，还需要模型版本等硬边界。[Redis语义缓存文档](https://redis.io/docs/latest/develop/use-cases/semantic-cache/)

本项目是Flutter客户端和本地SQLite，尚无需要多个应用服务器共享高并发缓存的证据。Redis会引入常驻服务、连接与部署配置、容量管理和恢复依赖；在移动端及离线使用场景下尤其不合算。即使它的向量功能有用，也不能据此证明这里需要再放一个数据库。**不引入是基于当前架构和未测得的收益，不是Redis能力不足。**

重新评估Redis的触发条件：产品实际引入共享后端、多个实例确有共同缓存/队列需求，并且测得本地方案或后端数据库成为瓶颈。此时比较部署成本、P95延迟、失效正确性与运维成本；不要仅以“支持AI”决策。

## 推荐缓存分层

| 层 | 是否需要 | 实现与边界 |
|---|---|---|
| 模型提供商前缀缓存 | 优先利用已有能力 | 保持稳定系统提示、工具定义在前，动态数据在后；无需本地Redis |
| 进程内精确结果缓存 | 有重复工作量证据后添加 | 小容量LRU，先缓存确定性、昂贵且可重算的解析结果；同请求合并需处理多个订阅者的独立取消 |
| 本地持久精确缓存 | 比Redis更适合本项目，先测再做 | SQLite保存经过结构校验的提取草稿；按容量清理、可随时丢弃，不进入业务同步 |
| 对话与任务检查点 | 应优先建设，属于持久状态而非缓存 | SQLite记录完成位置、输入版本、原始证据与待核对结果，不能随LRU淘汰，否则“清缓存”就丢任务 |
| 业务问答语义缓存 | 暂不采用 | “含税最低价”和“不含税最低价”、“不少于2”和“不多于2”语义很近，业务结果相反；价格变化也会使相同问题失效 |

DeepSeek官方说明前缀缓存默认开启，响应usage中提供命中/未命中token统计；缓存是尽力而为，输出仍重新生成，不保证100%命中。现有客户端只返回message，下一步可在共享核心保留usage元数据来测收益，不能把“默认支持”当作本项目已经测出缓存命中率。[DeepSeek上下文缓存](https://api-docs.deepseek.com/guides/kv_cache/)

应用侧精确缓存的建议键：`任务类型 + 原始输入哈希 + 提示/输出结构版本 + 供应商端点/模型标识 + 领域字典版本`。凡依赖物料候选或报价，还必须绑定实际数据版本/快照和币种、税口径、日期等条件。使用完整原文计算哈希，不能先去掉空格、标点或单位再计算，否则可能合并不同业务输入。模型别名升级无法仅靠名字识别，应设置失效版本、过期策略并允许强制重新生成。

只缓存通过现有领域校验的草稿，命中后仍执行当前校验，保留来源；不缓存失败、取消、截断响应，不把人工最终确认自动套给新来源。对话中的现价、预算、有效期和技术符合性继续由领域工具读取与计算，不能靠TTL保证正确。恢复数据库或切换库时应按本地库世代使派生缓存失效；缓存和任务数据库均需纳入现有恢复互斥约定，不能旁路恢复流程。

建议先采集重复输入比例、实际前缀命中token、调用延迟和失败重做次数，再决定是否投入持久精确缓存；目前没有这些测量，不提供“必然节省多少”承诺。

## 自动compact应该怎样做

OpenAI官方提供Responses的服务端阈值压缩和独立compact接口，用压缩项承接后续上下文。本项目使用DeepSeek兼容的Chat Completions路径，不能直接把OpenAI的参数或不透明压缩项塞入现有请求；“接口兼容”也不证明这部分能力兼容。可借鉴的是阈值触发、状态延续和接口分层的原则。[OpenAI Compaction](https://developers.openai.com/api/docs/guides/compaction)

建议在现有共享核心上增加一个轻量会话上下文组件，不另造每个页面各自的Agent框架：

1. **原始日志。** 完整问答、工具输入输出、本轮数据版本和用户修正存本机；先定义会话删除与保留策略。消息窗口只是发送给模型的视图，不是唯一存档。
2. **固定工作状态。** 当前目标、用户约束、选定项目/物料ID、已完成/待执行步骤、来源指针，尽量取自界面和业务对象。最新明确修正覆盖旧约束；摘要不能擅自改变数量、单位、币种、否定条件或用户确认状态。
3. **滚动记忆。** 保留最近完整轮次，将较早部分整理为带来源编号的结构化摘要；摘要是帮助理解追问的材料，不是授权、最新报价或确定事实。需要细节时按编号回查原文，当前业务结论仍重新查询。
4. **工具上下文整理。** 在完整工具调用批次结束后进行，保持调用/结果配对。优先去除重复结果和已消耗的大段明细；保存引用和必要总计。不能拿部分分页当全量，也不能丢掉尚待处理的工具结果。近期完整结果和正在引用的证据优先保留。
5. **自动阈值。** 以实际模型上下文容量扣除预留输出、工具模式与下一批结果后的可用量计算；建议先在约70%触发、整理到约45%–50%，这些是待调参起点。当前字符数不是token数，不能当精确模型容量；有官方token计量时使用计量，否则采用有余量的保守估算和显式模型能力配置。
6. **失败处理。** 总结先写暂存，验证后原子替换记忆，保留可回退版本；摘要失败不得清空会话或耗尽回答轮。可先用有来源的抽取式索引和原文回查降级；仍装不下时保存检查点、展示已完成部分并提供继续入口，不能静默失忆后假装完整回答。

语义摘要有成本和遗漏风险，不应每轮调用，也不应反复只摘要旧摘要。优先摘要新增的原始轮次，并定期从可追溯原文校准。触发compact会改变请求前缀，可能降低提供商缓存命中；稳定系统前缀、增量构建和阈值滞回比每轮重写整个提示更合理。保持正确连续性比追求缓存命中率重要。

这个方案包含“自动整理 + 外部原文记忆 + 回查”，不是无限扩大上下文。预算达到阈值时先整理或形成阶段产物；自主工具重复同参且数据版本未变化、没有新增有效信息时，及时停止重复查询并保留继续能力。硬上限仍用于防失控，日常长任务应由检查点接续，而不是要求用户重输。

## 五类AI能力分别处理

| 能力 | 连续性与缓存策略 |
|---|---|
| 报价提取 | 每段通过校验后保存草稿检查点，关联文件哈希、段号、输入版本；失败只重试该段。共享表头、供应商、币税条件由可核验原文上下文携带，不能仅靠摘要猜测 |
| 清单智能匹配 | 分离已提取项目和候选匹配阶段；恢复时候选库变化则只重做相关匹配，确认前重新检查报价。有限流程不需要聊天式无限历史 |
| 技术条款读取 | 精确缓存绑定原文、类别及参数字典版本；大输入分批时保持条款号，保留跨条款适用条件，确定性验约与人工核对不省略 |
| 参数提取 | 和条款使用同一执行与缓存协议；物料原文或类别变化就失效，禁止晚响应覆盖用户新编辑 |
| 数据对话 | 同一会话连续上下文、滚动记忆和证据回查；工具始终查询最新业务状态，旧答案仅帮助理解代词与目标 |

恢复任务还需做到：每次执行有run ID，输入或规则版本变化时原任务不能直接继续；已完成草稿不重复生成，落库继续使用现有事务与幂等约束。退出页面或关掉应用后是否继续执行，应显式表达当前行为；本轮仍是关闭页面会取消，不是后台持久任务。

## 后续顺序与验收

1. **P0：检查点和可恢复失败。** 第7段断网、取消、重启后从正确位置恢复；前6段不重付模型成本、不重复写业务记录。恢复/换库/输入编辑均能阻止旧任务继续应用。
2. **P0：对话上下文管理。** 覆盖超过6轮的代词追问、超过12k字符的单轮、超过64k工具结果；核对早期关键约束与后续修正。保存原文、回查成功、工具配对完整，摘要失败或上下文整理失败后可继续，不依赖人工反复重述。
3. **P1：采集usage与重复工作量，再加必要的精确缓存。** 验收模型/提示/字典/数据库版本变化必定失效，取消不污染缓存，清缓存不丢任务，含税/未税和相反比较关系绝不碰撞。
4. **暂缓Redis和语义答案缓存。** 等共享服务及实际吞吐需求出现，再做有基线的对比测试。

一条成功聊天、几次缓存命中、或者扩大预算后的单次导入，不足以证明“连续性已解决”。上面P0尚未实现，是本轮分析得出的明确后续工作；本轮交付的是预算纠正和完整取舍设计。
