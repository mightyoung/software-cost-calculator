# 自动上下文压缩实施记录

## 实施前计划

- 采用本机可逆的抽取式压缩：旧完整问答和完整工具批次移出模型窗口，留下原文摘录和稳定编号，通过只读 `recall_context` 分页/搜索取回。原始问答与本轮证据不删除、不改写。
- 保留系统规则、当前问题和尽可能多的近期完整轮次；在历史12k或总上下文48k字符阈值触发，分别向6k和32k整理，硬上限64k。字符阈值是当前适配器的保守产品边界，不宣称精确token计量。
- 压缩只在完整工具批次之间执行，永不拆散tool call/result。不给模型新增总结调用，不把历史数字变成当前事实，不增加Redis或依赖。
- 保持历史上传开关。UI自动显示整理进度，原历史展示与保存不受压缩影响。
- 先补完整性、回查边界与模型请求上限回归，再实现与接线；由独立审查检查证据和调用配对，最后运行核心及相关UI测试。

本轮不实现进程退出后的任务断点恢复、永久跨会话记忆或模型生成的语义摘要。`recall_context` 只可访问调用方已提供的历史和本轮查询，不读取其他会话或数据库文件。

## 已实现

[AssistantContext](../../packages/supplier_core/lib/src/assistant_context.dart)负责构建发送窗口和保存本次运行的原文副本；[对话核心](../../packages/supplier_core/lib/src/assistant.dart)在每次模型请求前自动调用它。小历史不再机械限制为6轮；较长历史按阈值整理，最新问题始终完整保留。

压缩采用“原文摘录 + 编号 + 回查”，不生成可能改写数量或条件的自由文本摘要。编号只在本次查询内有效；原始问答按已有页面机制保存在本机，最多100条消息的既有保留规则不变。压缩窗口不会覆盖它们。工具证据原文独立保留，不随上下文整理删除。

回查工具支持两种方式：按关键词搜索全部已提供原文，并返回命中位置和摘录；按编号与偏移分页读取完整原始JSON。分页不拆开Unicode代理对，非法编号、偏移和参数返回结构化错误。历史回查不能充当当前业务查询，也不会让历史中的记录编号自动获得已核验链接。

总窗口在48k字符触发整理，尽量回落到32k；历史在12k触发，尽量回落到6k。刚执行完、尚未送达模型的完整工具批次，如果能放进64k硬上限，则优先完整发送，允许暂时超过软阈值。超大批次仍保存完整原文并提供回查，而不是只留下一个不可恢复的错误。

**收尾同样可以回查。** 当已有归档上下文时，进入有限的只读回查阶段，而不是直接关掉全部工具。此前发送过的结果也适用，因为无状态的下一次请求不会自动记住已经移出窗口的内容。原有8个业务工具轮与24次业务工具调用保留，额外允许最多4个纯回查轮和8次回查调用，最后仍有总结机会；总模型调用不超过13次。混合业务与回查的轮次按业务轮计，超过额外回查预留也不会无限延长任务。

在窗口中省略内容不是完成阅读的证据。每份查询观察增加 `provided_to_model`：只有完整发送过的结果，或完整原文所有分页确实送达后，才可核验回答中的记录引用。查询依据仍能展示未送达的原文；最终回答带未读结果时附加不完整提示。这个标志证明传输范围，不证明模型理解或答案语义正确。

UI显示“正在整理对话上下文”，随后继续执行；整理无需额外LLM摘要调用。使用近期对话的开关与默认本机保留行为不变，停止仍会取消等待。页面说明已去掉不再准确的“最近最多6轮”。

## 明确的边界

1. 原文可恢复不等于模型推理无损。模型仍可能漏查、误读或用完有限轮次；达到上限时必须说明未确认范围，不能宣称全部读完。
2. 这是本次运行的自动上下文管理；页面关闭、程序退出后的任务恢复仍待实现。保存的页面历史与一次查询中的工具档案是不同的生命周期。
3. 没有引入Redis、持久语义缓存或后台自主任务，也没有把原始输入的大小上限、提供商配额和网络异常取消掉。
4. 字符阈值不是按实际模型token精确计费的窗口；后续可在提供商适配器加入usage和token估算，保持当前原文与回查协议。
