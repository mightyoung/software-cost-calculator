# 询价台账：对标成熟产品的批判性评审与改进建议

日期：2026-09-26
范围：v2 当前实现（`claude/project-research-95d005` 分支，含智能导入报价）
约束（不变）：≤30 人、≤90 台设备、至多每周交换一次、无服务器、每台设备独立运行，Windows 为主。

---

## 一、对标对象

| 类别 | 对标对象 | 借鉴点 |
|---|---|---|
| 开源 ERP 采购 | ERPNext（询价单 → 供应商报价 → 比价报表 → 下单） | 以询价单为中心的单据链；比价按物料分组并高亮最低单价；自带"最低单价 ≠ 最低总成本"的提醒 |
| 开源 ERP 采购 | Odoo（招标 / 备选询价单、供应商价目表） | 同一需求发给多家供应商、按行比较后分别授标；自动沉淀历史成交价 |
| 国内 SRM 询比价 | 正远、简道云等厂商的实践文章 | 统一报价口径（含税/税率）；报价有效期与截止时间分开管理；历史最高/最低/平均价与超价预警 |
| AI 报价比对 | BidLevel、Purchaser.ai、ProQsmart、EstimateHawk | AI 只做第一遍；每个值都能追溯到原件；把不同说法对齐到同一范围再比较；PDF 和图片是主要输入 |
| 本地优先软件 | Ink & Switch《Local-first software》、tonsky 的文件同步实践 | 按字段合并而不是整条记录覆盖；用逻辑时钟；通过共享文件夹同步时每台设备只写自己的文件；数据长期可用 |
| 物料主数据治理 | 大型集团物料主数据管控案例 | 一物一码；关键属性模板；新建时按关键属性查重；历史数据用映射表过渡 |
| LLM 文档抽取 | 人工复核实践（Parseur、Alan、EviSearch 等） | 值旁边显示原文出处；用确定性规则兜底模型"很自信但错了"的情况；复核界面快、支持键盘 |

说明：国内 SRM 资料多为厂商推广文章，本文只采用各家都提到的共识做法。

## 二、成熟产品的共同做法（提炼）

1. **单据链完整**：需求 → 询价（发给谁、何时截止）→ 报价 → 比价 → 定标（选谁、为什么）。每一步都留痕，事后能回答"为什么选他"。
2. **比价先统一口径**：含税与不含税、计量单位、运费、起订量都换算后再比；只比单价会误导。
3. **历史价格库是标配**：新报价自动对照历史最高、最低、平均价，超过红线就预警。
4. **主数据一物一码**：新建前按关键属性查重，已有的重复可以合并，合并后引用自动改指向。
5. **AI 只做第一遍，人来确认**：每个值可以追溯到原文；数字和型号用规则校验；只把拿不准的交给人看。
6. **原件要保存**：报价单 PDF、截图、邮件都作为证据挂在报价上。
7. **本地优先的同步**：按字段合并；冲突要让人看得见；每台设备写自己的文件，由汇总方合并；备份自动进行。
8. **报价时效有人管**：快过期的报价会提醒，不是等用到时才发现已经失效。

## 三、问题清单（按严重程度排序）

### P0：不解决，推到 90 台设备后会出事

**P0-1 多台设备会各自建出重复的供应商和物料，而软件没有任何合并手段。**
- 现状：每台设备各自新建"甲泵业""格兰富 CR10-5"，生成的 UUID 不同；交换时按 UUID 合并，两条记录都会保留。90 台设备各录几周，同一家供应商出现 5 到 10 个版本是必然结果（物料主数据的头号问题就是"一物多码"）。
- 智能导入只做精确匹配，只会让新建变得更容易，从而加剧这个问题。
- 后果：比价按物料分组，同一个物料被拆成好几份，"最低有效价"随之失真；预算里的"有更便宜报价"提醒也会漏报。

**P0-2 交换时按整条记录合并，而且版本号优先，会悄悄丢掉修改。**
- 证据：`exchange.dart` 以 `(version, updated_at, updated_by)` 整行比较，版本号排在最前。
- 场景一：A 机把某供应商改了两次（版本 3），B 机后来改了一次（版本 2），合并后 A 胜出，B 较新的修改丢失。
- 场景二：A 改了地址、B 改了备注，结果整条记录只保留一方。
- 现状只显示"冲突 N 条"，看不出丢了哪些字段、丢了什么值。
- 当初假设"同一条记录不会被同时编辑"。但一周的交换周期、30 个人共用一份供应商库，一周内两人改到同一个供应商的概率并不低。代码里已经有字段级变更日志（`change_log`），完全可以用来做字段级合并。

**P0-3 90 台设备之间的数据怎么传播，没有设计。**
- 现状：点对点导出整库快照（10 万条报价时约 126MB），没有记录"谁已经有了谁的数据"。每周两两交换时，一条新数据要经过好几周才能传到所有设备，而且每次都搬整个库。
- 成熟做法：在共享文件夹（网盘、NAS、U 盘都行）里，每台设备只写一个属于自己的文件，汇总时读取其他设备的文件合并，这样也不会出现网盘同步冲突。可以指定一台"汇总机"，再配合增量导出（只导出上次以来的变化）。

**P0-4 程序升级后交换会断：数据格式版本必须完全一致。**
- 证据：`schema_version` 不相等就拒绝导入，而且目前没有迁移机制。
- 90 台设备装的是未签名的安装包，也没有自动更新，不可能同时升级。一旦发布需要改表结构的版本，新旧设备之间就无法交换了。
- 另外，Windows 会对未签名的程序弹 SmartScreen 警告，在 90 台设备上会反复带来支持成本。

**P0-5 报价没有原件，事后无法复核。**
- 现状：智能导入写入之后，粘贴的原文就被丢弃了；手工录入也不能附带报价单 PDF 或截图。一旦对价格有争议，就拿不出依据。
- 成熟产品（BidLevel 等）的核心卖点之一，正是"每个值都能点回原件"。

### P1：影响日常效率和结果可信度

**P1-6 智能导入缺少可核对性：用户要么全信，要么全部重读原文。**
- 目前没有标出每个字段取自原文的哪一句，也没有任何置信度提示。最危险的情况是模型"很自信地"把单价或型号写错。
- 一个便宜但有效的办法：在本机检查单价、型号、电话等字段，确认它们在原文里真实出现（比较前统一去掉千分位、空格和全角字符）。找不到出处的字段标黄提示，这就是业界推荐的"用确定性规则兜底"。

**P1-7 实际最常见的输入格式不支持。**
- 供应商发来的多半是 PDF 报价单和微信截图，而目前只能处理粘贴的文字和 Excel。
- 这不需要上云：PDF 可以在本机提取文字层；图片可以用系统自带的文字识别（Windows OCR、macOS Vision、Android ML Kit），识别出的文字再走现有流程。

**P1-8 比价口径太窄，而且没有历史价格参考。**
- 只有币种、含税口径、单位都相同的报价才放在一起比。不含税报价按税率折成含税后本可以比较，现在却被分到另一组。
- 单位换算（台/套、米/千米）、运费、起订量、交期都没有纳入比较。ERPNext 的文档也专门提醒：单价最低不等于总成本最低。
- 没有显示该物料的历史最高、最低、平均价，也没有"比历史价高出 X%"的预警，而这是国内询比价系统的标配。

**P1-9 物料没有结构化，自动匹配靠运气。**
- 规格是一段自由文本，型号的写法也不统一（"CR10-5"和"CR 10-5"能对上，"CR10－5"用了全角的横线就对不上）。没有型号的物料要求名称、品牌、规格三项完全一致，实际上几乎匹配不到。
- 搜索只支持子串匹配，不支持拼音首字母和同义词，而中文用户很习惯用拼音首字母查找。
- 建议分两步：第一步给物料加"类别"字段，并统一型号的比较规则（去掉空格、横线，全角转半角，不区分大小写）；第二步再为常用类别配置 3 到 5 个关键属性，例如泵类的流量、扬程、材质。不必建设完整的物料主数据体系。

**P1-10 缺少"询价单"和"定标记录"。**
- 现在报价只是挂在项目下面的零散记录，回答不了几个常见问题：这批物料问了哪几家？谁还没回复？最后选了谁，理由是什么？
- 轻量做法：
  - "询价批次" = 项目 + 需要询价的物料 + 发给了哪些供应商 + 截止日期，报价回来后自动归到对应批次；
  - "定标" = 选中的报价 + 一句理由。
- 这两样东西也会让"待询价清单"这个导出功能真正闭环。

**P1-11 报价时效是被动发现的。**
- 只有在打开项目预算时才会看到"报价已失效"，缺少一个总览：未来 30 天将要过期的报价、超过 90 天未更新的物料。

### P2：应当做，但不紧急

**P2-12 交换文件明文包含全部价格和联系人。** 这个文件会通过 U 盘或微信传输，丢失就等于全部泄露。可以提供可选的口令加密，用本地加密库即可，不需要服务器。

**P2-13 身份和问责较弱。** `updated_by` 记录的是设备名，而且可以随手修改；询价人是自由填写的文本。30 个人使用时，变更记录里看不出"是谁改的"。可以在设置里填写使用人，并在变更记录中显示。

**P2-14 备份靠自觉。** 应该每天自动在本机做一次快照，并只保留最近 7 天。

**P2-15 验证欠账。** 真机运行 0 次，真实 DeepSeek 调用 0 次，多设备交换演练 0 次。10 万条报价规模下，界面每按一次键就做一次 LIKE 查询，速度从未实测。组件测试覆盖也偏少。

**P2-16 预算没有版本或基线。** 投标时算的版本和执行中的版本混在一起，变更记录只到单个字段，没有"这一版预算"的概念。

## 四、明确不建议照搬的

这些是大型 ERP/SRM 的标配，但对这个团队规模和"无服务器"约束来说属于过度设计：

- 供应商门户、在线报价、密封报价、防串标：都需要服务器，而且团队规模用不上。
- 采购订单、收货、三单匹配、审批流：已经超出"询价和成本"的定位。
- 完整的物料主数据编码体系和数据治理委员会：用"类别 + 关键属性 + 查重合并"就能覆盖 80% 的需求。
- 引入 Automerge 等 CRDT 库：数据都是一个个独立字段，没有协同编辑的长文本，"字段级合并 + 逻辑时钟"已经足够。
- 为 AI 做多模型投票或置信度模型：用"原文出处校验 + 人工确认"就能达到目的，成本低一个数量级。

## 五、改进路线

以用户价值和风险排序，每一阶段都可以单独交付：

**阶段 A：推广前止血（先于 90 台部署）**
1. 重复数据合并工具：选定要保留的记录，把其余记录合并进来，所有引用自动改指向，合并本身也会随交换传播。同时在新建和导入时给出"疑似重复"提示（名称互相包含、型号统一比较规则后相同）。（P0-1）
2. 交换改为字段级合并：基于已有的 `change_log` 和逻辑时钟逐字段取较新值；真正的冲突（同一字段两边都改过）列出来，让用户选择保留哪个。（P0-2）
3. 数据格式迁移：能读取旧版本的数据并就地升级；导入旧版本的交换文件时先迁移再合并；只拒绝比本机更新的格式，并提示对方先升级。（P0-4）
4. 每天自动本机快照。（P2-14）
5. 先找 3 到 5 台设备试点 2 周，其中包括一次跨设备交换演练和真实的 DeepSeek 调用，再扩大到 90 台。（P2-15）

**阶段 B：可信度**
6. 报价附件：原件存放在本机的附件目录，交换时一起带过去（可以设置单个文件大小上限）；智能导入会自动把粘贴的原文作为附件保存。（P0-5）
7. 智能导入的原文出处校验：数字和型号必须能在原文里找到，找不到就标黄；核对页点一个字段就高亮对应原文。（P1-6）
8. 比价口径换算：含税与不含税按税率换算；允许配置单位换算；显示历史最高、最低、平均价，并对超出历史价一定比例的报价预警。（P1-8）
9. 询价批次和定标记录。（P1-10）
10. 过期报价提醒总览。（P1-11）

**阶段 C：覆盖和运维**
11. 支持 PDF 文字层和图片 OCR 输入，均使用各平台自带的能力。（P1-7）
12. 共享文件夹同步模式：每台设备写自己的文件，并支持增量导出。（P0-3）
13. 交换文件口令加密。（P2-12）
14. 物料类别和关键属性模板，搜索支持拼音首字母。（P1-9）
15. 在设置中填写使用人；为 Windows 安装包做代码签名，并提供一个统一的"检查更新"入口（例如读取共享文件夹里的版本清单）。（P2-13、P0-4）

## 六、结论

- **已经做对的**：本地优先、精确小数、写入前人工确认、API Key 放在系统安全存储、只读的 AI 工具。这些方向与成熟产品一致。
- **最大的风险不在功能多少，而在多设备协作的"数据质量"**：重复的主数据、整条记录合并悄悄丢改动、升级后交换中断。这三个问题在 1 台设备上看不出来，推广到 90 台之后会集中暴露，而且事后很难清理。所以建议先完成阶段 A，再扩大部署。
