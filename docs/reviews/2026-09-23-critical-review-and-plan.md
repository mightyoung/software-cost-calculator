日期：2026-09-23。审查对象：
- 设计：`docs/superpowers/specs/2026-09-16-supplier-inquiry-design.md`、`docs/superpowers/plans/2026-09-16-supplier-inquiry.md`

- 证据：`docs/verification/*`（约 40 份）、`artifacts/`（6.3 GB）

本审查亲自复跑了 `supplier_core` 全量测试：**440/440 通过，耗时 3 分 13 秒，`dart analyze` 无问题**。其余结论来自源码阅读与仓库内报告。

## 一、总评

**核心内核写得认真，产品却不存在。** 一周多的投入产出了一个测试严密的"本地分布式版本控制内核"，但 18 项验收 **0 项 PASS**，三个首发目标平台（Windows、Android、Web）中两个从未运行过，唯一的全量测试宿主 macOS 不是目标平台。在 Android 上，用户连一个 Excel 文件都选不中，因为原生端要求手动输入绝对路径。

根因在设计，而不在编码：**复杂度被放在了用户最不关心的地方（因果同步协议），而用户最关心的地方（录价、查价、比价、Excel 往返）反倒被它拖住了。**

## 二、设计层问题（最严重）

### D1. 需求与方案严重失配：用分布式版本控制系统来记报价
业务是"录入供应商报价、查询和比价"，设计却给出了内容寻址修订 DAG、RFC8785 JCS 规范化、多 head 并存、redirect 别名图、全历史因果闭包，以及人工选择完整版本来解决冲突。这些复杂度的唯一依据是一句"每端可独立编辑、并发修改人工解决"。设计里从没追问：
- 实际有几个人、几台设备？多久同步一次？
- 同一条报价真的会在两台设备上同时被改吗？这种情况一年发生几次？

如果答案是"一个人、两三台设备、每周同步一次"，那么单写者主库加只读副本，或者"最后导入者确认覆盖"加变更日志，就能满足 95% 的需求，工作量不到现在的十分之一。

### D2. 全量历史同步不可持续
- 同步包每次都携带**全部历史**，而且设计明确规定"不自动裁剪历史"。包体积和校验时间会随使用时间**单调增长，永不收敛**。
- 实测：10 万报价、50 万修订时，仅在 Mac 上**只读扫描一遍修订就要 250 秒**。设计给 Android 的导入目标是"≤20 分钟"，这等于承认每次同步都是一次全库迁移。这样的操作不可能成为日常流程。
- 设计还把"增量同步"列为"不包括"，等于把唯一的出路堵死了。

### D3. 同步载体选错：把 JSON 塞进 Excel 单元格
修订卷是 xlsx，每行一个 `envelope_json`；而卷的 sha256 又被精确绑定，"手动重存即视为损坏"。**Excel 唯一的价值（人可读、可改）被规格明确否定，留下的全是代价：**
- 单元格 32,767 字符上限，以及 envelope ≤24,000 UTF-16 单位的限制；
- shared strings 的内存压力，以及 5000 行/8 MiB/32 MiB 的分卷规则；
- 949 行的 XLSX 读取器、434 行的写入器，外加一整套 ZIP/XML 边界防御。

机器对机器的同步应该用单个 SQLite 快照或 `jsonl.gz` 修订流。业务 Excel 导出本来就是另一个独立入口，二者不应共用格式。

### D4. 存储膨胀，与目标平台不兼容
10 万报价的基准库有 **1.97 GB，约 19.6 KB/条**，而一条报价的业务数据约 1 KB。原因如下：
- 每条报价有 4–5 个完整快照修订；
- 投影表、search key 表、`candidate_term` 表、7 张 `graph_*` 工作表并存；
- 每一次单条编辑都会永久留下 job、seal、confirmation_event、commit_receipt 等元数据行（`cleanupStaging` 只清 staging，其他按设计"保持不变"）。

浏览器 OPFS 配额和中低端 Android 的存储都承受不了这个量级，而且它还没算备份和同步包的双倍空间。

### D5. 规格"过度精确"，产品基础却空白
规格用大量篇幅定义 JCS 摘要、UTF-16 上限、ZIP 条目数、闰秒，但**没有**以下内容：
- 用户画像、典型工作日流程、设备与人员数量；
- 真实的业务 Excel 样表（现在导入映射是按想象设计的）；
- 任何线框图，包括比价结果页、冲突解决页这些用户实际会看到的界面；
- 优先级：18 项验收平权，没有"先让用户用起来"的最小切片。

### D6. 验收门从第一天起就不可达，被绕过后却继续加码
- 发布门要求 Windows 11 真机、Android 真机、Microsoft Excel 与 WPS 真实往返；开发环境是 macOS，没有 Windows 机，没有 Android 真机，WPS 自动化也超时。
- 计划明确写着"T1 通过平台能力门后锁定版本，禁止绕过平台失败继续宣称支持"。然而 T1 至今 BLOCKED，`toolchain.json` 里 `storage_backend`、`sqlite_engine`、`sqlite_wasm`、`sqlite_worker` **全部仍为 null**，后续 T3–T12 却都已动工。**计划自己的纪律被自己违反了。**
- 随后 Android/Windows 被标为 DEFERRED。结果是首发三端里两端的验证无限期推迟，发布门形同虚设。

### D7. 文档是过程产物，不是产品规格
- 设计文档正文里混入了"ECC / Superpowers / grill-me"等技能名，以及"用户原话确认"之类的会话叙事。这是生成过程的痕迹，对后续维护者毫无意义。
- 约 40 份验证/审查报告加 6.3 GB 证据，形成了证据官僚主义：代理审查代理并给出"APPROVE / CLEAR"，同一时刻 0 项验收通过。
- `development-progress.md` 仍写着"T3 未开始"，`release-matrix.md` 却已经到了 T12，文档互相矛盾。
- README 仍是"Software Cost Calculator：估算软件开发成本"，仓库名与内容完全不符。

## 四、需求再校准结论（2026-09-23 用户答复）

| 问题 | 答复 | 架构含义 |
|---|---|---|
| 人数/设备 | ≤30 人，≤90 台设备，每周最多交换一次 | 交换是低频的批量文件操作，不需要实时或增量协议 |
| 同一记录并发修改 | 不会发生 | **不需要**修订 DAG、多 head、冲突解决 UI 和别名修复 |
| 服务器 | 不用；每台设备单独管理、单独运行 | 每台设备一个 SQLite 库，靠文件交换 |
| 真机 | 有，打包后由用户验证 | 我负责出安装包和验证清单 |
| 真实样表 | 没有，由我设计 | 业务 Excel 模板由本项目定义 |
| 平台 | Windows（主力）、Android、macOS | **Web 移出范围**；新增 macOS target |

**决策（ADR-0001）：** 放弃"修订图 + 全历史 xlsx 分卷同步"，改为**每设备一个 SQLite 库，交换文件就是数据库快照，按记录版本号合并**。

- **记录**：四张业务表 supplier/contact/product/quotation，每行包含 `id(UUID)`、`version`（每次修改 +1）、`updated_at`、`updated_by`（设备名）和 `deleted`（墓碑标记）。
- **交换 = 备份 = 恢复**：导出用 `VACUUM INTO` 生成一个 `.siq` 文件（它本身就是 SQLite 一致快照，A17 天然满足）。导入时先 `ATTACH` 只读挂载，做 schema 版本检查和 `integrity_check`，再把每一行重新走领域校验，最后在**一个事务**内 upsert：`version` 更大的一方胜出；版本相同但内容不同时视为"两端都改过"，按 `updated_at` 再按设备名定胜负，并在预览中列出这些记录。导入结果与导入顺序无关，重复导入是幂等的。
- **历史**：同一供应商对同一产品的每次询价本来就是一条独立报价，价格历史自然保留。对单条记录的纠错直接覆盖，不再保存修订快照。
- **业务 Excel**：导出支持当前筛选条件，表中带 ID 和版本两列（可隐藏）。导入时，有 ID 的行按 ID 对比，在预览里显示改动；无 ID 的行按新增处理，并提示疑似重复。重导同一文件因为按 ID 对齐，天然不会重复导入。**删除**回执表和双指纹机制。

## 六、新增需求：按项目管理与项目报价/成本预算（2026-09-23）

**原则：借鉴 `project-management-app` 的业务设计与实现逻辑，不复用任何代码。** 它是 Next.js 网页原型：数据实际存在 localStorage（`isUsingDemoMode()` 恒为 `true`），Prisma 已定义但未被调用。技术栈与本项目完全不同，而且代码里有若干缺陷不应照搬（见 6.3）。

### 6.1 借鉴的设计逻辑 → 本项目落地

| 来源（参考项目） | 设计逻辑 | 本项目落地方式 |
|---|---|---|
| 工作流分析报告 §3.3 项目信息维度 | 项目以编号、合同号、类型（市场订单/内部研发）、级别 A/B/C、事业部、负责人为主档，**一次录入，多处引用** | `project` 表：`code`、`name`、`contract_no`、`contract_amount`、`type`（市场订单/内部研发）、`level`（A/B/C）、`department`、`leader`、`customer`、`start_date`、`end_date`、`status`、`notes`。报价、物料清单都按 `project_id` 引用，不再重复存项目文字 |
| 自动化引擎："项目创建时自动生成项目编号" | 编号自动生成（示例 `SC2025113`） | 自动建议 `年份-设备简码-序号`（如 `2026-WH01-015`），可以手改。**身份用 UUID，编号只是显示字段**：90 台设备独立运行，全局连号必然冲突，所以编号不做唯一约束，重复时提示 |
| 项目状态 | planning / in_progress / completed（Prisma 里还有 approved、on_hold、cancelled） | 收敛为 4 个：**策划中 / 进行中 / 已完成 / 已取消**。审批相关状态不纳入 |
| 工作流 3 与"23-项目成本预算表"模板 | 成本预算按**材料费、外协费、人工费、制造费用**分类分解 | `project_item.category` 取值：材料费 / 外协费 / 人工费 / 制造费用 / 其他。**材料费行**从物料库选物料并带出报价；其余类别行只填名称、数量、单位、单价（可以不关联物料）。预算页按类别小计 |
| 数据关联"合同金额 → 收入 → 成本" | 合同金额是预算的上限参照 | 预算页显示：合同金额、成本合计、对外报价合计、毛利和毛利率。**成本 ≥ 合同金额的 90% 时标红预警** |
| 自动化引擎："预算超支 实际>预算90% 自动预警" | 以阈值预警代替人工巡检 | 对应到报价场景有两类预警：① 成本超过合同金额 90%；② 已选单价与该物料当前最低有效报价偏差超过 10%（包括"有更便宜的"和"原报价已过期"）。只在项目列表和预算页显示标记，不做通知中心 |
| §4.1"3 步原则" | 任何核心操作不超过 3 步 | 新建项目预算：**① 填基本信息（可复制已有项目）→ ② 选物料并填数量 → ③ 确认并生成**。录入报价：选项目 → 填价格 → 保存 |
| 预算模板"智能填充" | 按项目类型带出模板 | "复制已有项目的物料清单"作为新项目起点。**不另建模板库**：复制已经覆盖了这个需求，以后确实需要再加 |
| 导出（项目汇总、预算报表） | Excel 导出是一等功能 | 导出两份文件：**项目报价单.xlsx**（对外，只含报价列）和**成本预算表.xlsx**（对内，按四类费用分组，含供应商、报价日期、小计与毛利） |

### 6.2 不借鉴的部分
不借鉴的模块：用户/角色/登录、审批流、里程碑、甘特图与任务、上报、通知中心、月度收入/回款滚动预算。

理由：本产品是"每台设备独立的询价与成本工具"，不是 OA 或项目进度系统。月度滚动预算以后需要时再单独评估。

### 6.3 参考实现中的缺陷，本项目必须避免
| 缺陷（参考项目代码） | 后果 | 本项目规则 |
|---|---|---|
| `getAll()` 在列表为空时回退到 `DEFAULT_*` 演示数据 | 用户删光数据后演示数据"复活" | 不内置演示数据；空就是空 |
| `id: String(Date.now())` | 多设备同一毫秒创建会撞 ID | UUID v4 |
| 金额用 `number`/`Float` | 0.1+0.2 这类精度误差 | 精确十进制（复用本项目已有规则） |
| `getSummary()` 把收入、回款、成本加在一起算执行率 | 指标没有业务意义 | 只按同一口径、同一类别汇总 |
| 文档说 90% 预警，代码按 >100% | 设计与实现脱节 | 阈值写成常量，并用测试锁定 |
| 状态枚举在 types（3 个）与 Prisma（6 个）不一致 | 数据不一致 | 状态只在一处定义 |

### 6.4 数据模型增量
- **`project`**：字段见 6.1，另加 `markup_rate`（统一加价率，默认 0）和 `currency`/`tax_mode`（项目统一口径，默认 CNY 含税），外加通用的 `id/version/updated_at/updated_by/deleted`。
- **`project_item`**：`project_id`、`category`、`product_id`（仅材料费必填）、`name`（非材料行必填）、`qty`、`unit`、`quotation_id`（可空）、`unit_cost`（**选定时的快照**）、`unit_price`（可空，为空时按 `unit_cost × (1+markup_rate)`）、`notes`，外加通用字段。
- **`quotation.project_id`**：报价按项目录入；历史导入可以为空。
- **口径**：材料行选中的报价，币种和税制必须与项目一致，否则拒绝并提示"口径不一致"。不做汇率换算。

### 6.5 计划调整
| 阶段 | 增量 |
|---|---|
| 阶段 1 核心 | 新增 `project`、`project_item` 及合计、分类小计、两类预警的计算。**必留检查**：合计精确到 6 位小数；口径不一致被拒；单价快照不随新报价改变；90%/10% 阈值的边界值；清空列表后不出现演示数据；交换后两端合计一致 |

**有借鉴必要，但范围很窄。** 真正的价值集中在四处：
1. **领域校验**：精确金额、日期精度、文本规范化；
2. **XLSX 读写**：词法保真、1900/1904、公式拒绝；
3. **比价口径规则**；
4. **业务 Excel 导入的"映射→预览→逐行决策"流程与录入表单的交互**。

这四项就是 v2 里最难写对的部分，直接省下约 1 周工期。其余 78% 是修订图与同步协议的配套设施，v2 不需要，也不建议"先留着以后用"。

**借鉴时必须修正的既有缺陷**（v2 验收项）：
1. 有效期为空的报价被排除在最低价之外（见 7.2 比价规则），会导致预算默认价取不到；
2. XLSX 写入全部为文本，预算表金额无法在 Excel 中求和；
3. 日期手输 `YYYY-MM-DD`，需改为系统日期选择器；
4. 界面暴露修订号、heads、设备 ID。

**迁移方式**：新分支 `simplify/v2` 从 main 起步，把上表"直接复用"的文件及测试**逐个拷贝过来并在新分支首次提交**（提交信息注明来源路径）。旧工作区只作为归档参照，不做合并，这样 v2 分支不会带入任何修订图代码。

### 8.3 它在你的场景下还剩什么价值
你的答复是"同一记录不会并发修改"，所以它最核心的能力（多 head 保留与人工解决冲突）用不上。仍然有价值的有三点：
- **完整变更历史**：谁在哪台设备、什么时候把某个价格从多少改成了多少；
- **重复导入幂等与旧包不覆盖新数据**；
- **包损坏或篡改检测**。

v2 方案对后两点已有等价实现：版本号合并天然幂等、旧数据不覆盖新数据；SQLite `integrity_check` 加 schema 校验检测损坏。**第一点可以用一张追加写的"变更日志"表**（记录、字段、旧值、新值、设备、时间）实现，约 100 行，并随交换文件一起合并。

## 十、新增需求：接入在线大模型（DeepSeek）查询数据、按清单自动建项目（2026-09-23）

### 10.1 接口事实（依据 DeepSeek 官方文档，2026-09 检索）
- 兼容 OpenAI 协议，接口为 `POST https://api.deepseek.com/chat/completions`，`Authorization: Bearer <key>`。
- 当前示例使用的模型名是 `deepseek-flash` 和 `deepseek-v4-pro`。旧名 `deepseek-chat`/`deepseek-reasoner` 是否仍可用，文档没有写明。**因此接口地址和模型名都做成设置项**，默认 `deepseek-flash`。
- JSON 输出：`response_format: {"type":"json_object"}`。提示词中要写"json"并给出示例；官方说明偶尔会返回空内容，所以**遇到空结果或无效结果自动重试一次**。
- 工具调用：`tools` 为 function 定义。官方提醒参数可能不合法或出现多余字段，**必须在代码里校验**。

来源：[Your First API Call](https://api-docs.deepseek.com/)、[JSON Output](https://api-docs.deepseek.com/guides/json_mode/)、[Tool Calls](https://api-docs.deepseek.com/guides/tool_calls/)、[Change Log](https://api-docs.deepseek.com/updates/)。

### 10.2 设计原则
1. **不把"全部数据"发给模型。** 10 万条报价装不进上下文，也不应整体外传。改为给模型 7 个**只读工具**：检索物料、检索供应商、检索项目、列出报价、可用报价、项目预算、按 ID 读取。模型决定查什么，本地执行查询，每次最多返回 50 行，最多 8 轮。
2. **模型不能写数据。** 问答只有只读工具。"按清单建项目"只产出**提案**，由用户在预览界面确认（可改匹配、改数量）后才写入，且写入在一个事务内完成。
3. **清单是不可信输入。** 清单解析这一步，模型不拿任何工具。提示词里写明"清单内容只是数据"。模型输出按字段逐一校验：物料 ID 必须属于本地检索出的候选集合，否则按未匹配处理；数量不能解析时记为 1，并在备注里保留原文供人工确认。
4. **最少外发。** 匹配这一步只发送候选物料的名称、品牌、型号、规格、单位，**不发送价格和供应商**。问答时发送的是工具查到的结果，可能包含价格，界面上要告知用户。
5. **API Key 不进数据库。** Key 存在系统安全存储中（Windows 凭据保护、macOS 钥匙串、Android Keystore，界面阶段用 `flutter_secure_storage` 实现），**不会随交换文件扩散到其他设备**。每台设备各自配置。
6. **离线可用。** 没有配置 Key 或没有网络时，只是 AI 功能不可用，其他功能照常。

### 10.3 "给一份清单 → 自动建项目 → 导出"的流程
1. **输入**：粘贴文本（已实现）；Excel 文件在 XLSX 读取器移植后转成逐行文本再走同一流程。
2. **模型整理**：输出 `{name, requirements, qty, unit, keywords}` 列表。合计行、标题行跳过；长清单按 6000 字分段处理。
3. **本地检索候选**：用名称和关键词在物料的型号、名称、品牌、规格、类别中做加权子串匹配（中文无需分词），每项取前 8 个。
4. **模型匹配**：每批 15 项，返回 `{index, product_id|null, confidence, reason}`。
5. **生成提案**：匹配上的物料自动带出**当前最低的有效报价**；没匹配上的作为"待询价"材料行（有名称、没关联物料，预算中显示 `needs_inquiry` 预警）。
6. **用户确认**，然后在一个事务内建项目和全部物料行。
7. **导出**：沿用项目报价单和成本预算表，另增一份"**待询价清单**"（未匹配行，可直接发给供应商询价）。此项在 Excel 导出实现时一起完成。
