# 本地供应商与询价系统：三视角研判

状态：三轮业务问答及综合设计整体审阅均已完成，用户确认定稿并编写开发计划。

## 证据与方法

ECC：独立 Architect 依据 backend-patterns 检查本地服务、仓储、事务、查询与恢复。Superpowers：独立 Analyst 依据 brainstorming / writing-plans 检查范围、选项、交付闭环和证据。grill-me：主代理按其指向的 grilling 实施分轮访谈，业务决定由用户回答，不以代理意见代替。

读取现 PRD、同步v1、验收规范、阶段0新增字段方案及小样报告。现小样已有19项测试及独立审查报告；本轮没有重跑这些测试，也没有把历史通过说成本轮新结果。

## 第一轮已由用户确认

| 决策 | 用户答案 | 设计影响 |
|---|---|---|
| 多端编辑 | 允许独立编辑，冲突人工处理 | 保留因果追踪、旧包识别和并发版本保留；不按设备时间覆盖 |
| 询价组织 | 每条报价独立记录项目及询价信息 | 保留报价级上下文，不新建询价单主表 |
| 三年报价规模 | 1万—10万条 | 必须以10万报价及历史修订进行容量设计；旧20MiB全库上限不满足目标 |
| 首版移动平台 | Android，iPhone后续 | 首版Windows/Android/Web；iOS保留共享核心与适配边界，单独后续验收 |

## ECC 研判

可保留：本地应用服务表达业务意图、仓储隔离持久化、单事务提交、批量查询避免N+1、结构化本地批次错误。无需HTTP服务器、Redis、账号或授权中间件。

需要修改：20MiB只可作为候选分卷大小，不能继续作为全部本地业务写入的上限。旧方案所有动作均检查全库预算，满额时连删除、冲突修复也可能拒绝，形成无法处理问题的状态。容量必须分别规定业务数据库、历史、单卷、整包和暂存空间。

数学证据：旧预算B为1MiB固定项加每单元格256字节结构预留及2倍转义文本。新增六列后报价投影25列，再加一条修订4列，每报价仅结构预留就7424字节，尚未计正文、共享实体和多次修订。20MiB减固定项最多容纳约2683个这样的最小组合，不能支撑1万—10万条报价。此为规范公式下界，不是真实压缩文件或内存测量。

已采用方向：完整修订集合分卷，全部卷齐备并验证后再单次业务提交；暂存可分批落本地但不对业务查询可见。增量交换另需缺祖先/补包/基线契约，不可只发部分历史却宣称自包含。第二轮用户已确认ZIP内含Excel分卷的全量交换。

## Superpowers 研判

核心问题：当前技术阶段缺少可独立使用的产品出口，应按“本地工作版→多端交换版→首版三端验收”组织交付；平台工具链准备提前开展。Dart技术页不能冒充Flutter产品壳。

补齐需求：Excel是否用于人工修改后回流；没有价格的询价是否保存；新增字段哪些必填；真实数据规模与满额策略。前轮已确认自由多端编辑与独立报价，不再保留与这些答案冲突的方案。

避免不必要兼容成本：原v1是规划与golden证据，不等于已发布用户协议。保持旧证据不可变与承诺永久支持正式v1数据是两件事；新发布协议应独立编号，不能自动引入未经验证的混合版本历史。

保留明确验收：新增项目/询价字段必须贯穿录入、编辑、组合筛选、导出和同步；“同一条纠错”“新一次询价”“重复文件重导”分别验证。备份、离线重启、迁移失败、预览过期及真实文件软件往返都是独立发布门。

## grill-me 研判与用户决策

已收敛的设计树：独立多端编辑→需要冲突保留；独立报价→上下文继续放报价；10万规模→不能沿用全库单包限制；Android首发→三端先验收。

第二轮用户已明确：

1. 支持Excel/WPS修改业务表，经预览确认修改原记录或新增一次询价。
2. 只保存已经取得价格的报价，不做待回复或不报价流程。
3. 新录入项目名称或编号至少一项、询价时间、询价人必填；地点选填。
4. 接受ZIP内含Excel分卷，首版全量交换，不做增量基线管理。

第三轮用户已确认：允许显式历史资料导入例外，保留上下文缺失；允许仅日期与具体时刻并存，不虚构00:00。设计使用standard/historical创建模式和date/instant/unknown时间精度，区分新建规则、历史未知与真实时刻。

## 综合候选设计

保留Flutter共享核心方向，但依赖锁定以三端真实验证为前提；本地服务处理录入、纠错、复制新询价、导入预览、提交、冲突解决与备份。查询从可重建投影读取，历史身份与业务候选筛重分开。数据精度、错误可见、事务一致性沿用已验证原则。
