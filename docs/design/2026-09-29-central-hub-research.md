# Rust 中心端：首轮研究与讨论稿

日期：2026-09-29。代码基线：`1138e2cad37f265b648144a0793f647f23dd30e7`，独立分支 `codex-backend`。本文记录研究、用户已确认要求与候选设计；用户随后明确授权按当前设计开始开发。首批范围与验证记录见 `docs/superpowers/plans/2026-09-29-central-hub-v1.md`，不把所有候选能力都视为已经实现。

## 已确认的目标

同一公司多个项目和同事共享供应商、历史询价、项目成果；客户端保留跨平台、单机独立处理能力，中心端可选。共享由用户明确发布，选择供应商、询价记录或项目成果后进入公司资料库。服务端使用 Rust，要求高效、集中、稳定，控制维护成本。

用户进一步确认：首要价值是找到可靠供应商、查到可参考的历史报价；高阶能力为根据技术要求自主选型。服务端需要在两张网络分别部署并支持跨网数据同步。

已确认跨网为严格单向：A 可以发送，B 无法返回任何信息。传输方式为来源端指定目录中的文件定期单向传入内网指定目录；内网中心扫描接收目录并导入。用户已确认服务端是否启用双网同步由配置决定；启用后，全部已发布到公司共享库的资料默认进入内网投递流程，不增加逐条跨网勾选。本地未发布草稿不在共享范围内。仍需讨论：发布后的更新是否需要再次确认、预计设备数和数据规模、附件需求、资料撤回与保留期限。以下推荐不等于这些问题已经定案。

## 已确认优先级对应的功能建议

### 先做好可靠供应商与历史报价

供应商资料页应回答“能提供什么、谁曾接触过、何时得到什么反馈、依据在哪里”。建议展示相关物料、历史询价、来源项目、信息更新时间以及有依据的合作评价。实际成交、交付表现、质量问题只能在有对应数据时展示；询过价不等于合作过，也不等于供应商可靠。资料不足应明确标注，不凭记录数或 AI 推测生成可靠度分数。

历史报价检索应同时保留型号/规格、单位、数量条件、报价日期、币种、税运口径和有效期等已知条件。字段缺失时标记未知；有依据才做换算。默认展示原报价和可比性说明，避免把不同范围的价格简单平均为所谓参考价。原始询价依据与所引用的发布版本应可追溯。

首版成果指标可从真实使用任务定义：能否找到相关供应商并追溯推荐依据；能否找到条件相近的报价并说清差异；能否在本地项目中引用后保留当时价格和来源。具体耗时与规模阈值待样本和部署规模确认后制定。

### 高阶：按技术要求自主选型

建议逐步形成“解析要求 → 结构化约束 → 检索候选 → 校验硬性要求 → 排序 → 解释差异 → 形成可编辑选型结果”的流程。中心提供跨项目积累的物料参数、供应商和报价证据；客户端继续具备在已下载资料范围内独立选型的能力。

硬性条件不满足的候选应剔除或明确列入偏离方案；关键参数未知不能当成满足。候选排序可考虑规格符合度、信息新鲜度、可比价格和有依据的合作表现，权重由后续业务讨论决定。模型可辅助解析与解释，结构化规则和来源记录承担可复核的判定。自动形成推荐方案与自动确认采购分开设计；用户尚未要求采购执行能力。

结果应记录要求版本、参数/规则版本、资料版本、未满足项与未知项。同一份方案在另一张网无法访问原始资料时，仍应能依据随包携带的必要快照复核。是否增加中心后台选型任务尚未定案，避免先复制客户端业务引擎。

## 双网中心：新增架构约束

建议两张网各有独立可工作的中心实例，各自服务本网客户端、保存本网已发布资料并建立索引。跨网中断不应阻塞本网发布、检索和本地使用。中心之间交换允许跨网的发布资料及其版本，不直接复制整个运行数据库。

跨网范围与公司共享范围一致：启用双网同步后，A 的全部已发布资料默认单向投递到 B，不设置逐条跨网选择或额外发布审批。本文用 A 表示来源网中心、B 表示用户已明确的内网接收中心。A → B 汇入资料；B 本地产生的资料默认无法回到 A，不承诺两端全量一致。

用户进一步确认是严格单向、B 完全不能回传。跨网流程不能依赖查询 B、接收确认或双方协商检查点。本网客户端与本网中心的发布流程仍可以使用正常回执；这一能力不延伸到跨网链路。

严格单向情况下的候选方案：A 保存允许跨网的不可变发布版本与可重发批次；批次带清单、范围和内容摘要；B 持久去重、校验依赖及完整性后入库。A 按约定重复发送和定期发送可重建当前共享资料的基线，B 显示缺失项与导入错误。增量重发窗口、基线范围和保留期限需要结合数据规模定义；如需恢复完整历史，必须另有覆盖历史的归档或重发安排，不能仅靠当前基线。没有反向通道时，A 无法依据 B 的实际缺失项自动定向补传，也不能保证任意长断网后一定完整恢复；须由预设重发/基线机制或操作人员在 A 发起补发。传输协议需适配实际单向设备支持的接口，不能预设普通 HTTP/TCP 可跨越无回程链路。

接收端建议分开保存 A 的原始发布版本与 B 的本地评价、补充和派生资料。A 更新原始资料时保留 B 的补充；B 的修改不伪装成 A 的新版本。A 撤回共享资料可作为有版本的事件传入 B，但不自动删除 B 的独立成果与已采用的历史报价快照。

候选协议要求及其适用条件包括：

- 原始发布 ID、来源中心、版本、必要引用、内容摘要和协议版本；转发保留原始身份，不把收到的数据重新伪装成本中心的新发布。
- 持久保存发送任务、接收记录及进度；重试同一版本不重复入库。相同 ID/版本出现不同内容时作为异常处理。
- 接收完成并校验后再使资料可见；必要附件未到齐时显示待完成。索引可以重建，原始发布版本保留。
- A 只显示本地已导出、已提交传输等自身可证明状态，不显示未经回程证据支持的“B 已接收”。B 单独显示已收到、校验失败、待补齐、已入库和已可检索。
- 接收按原始发布身份去重，恢复后允许重放，保留期限造成缺口时支持重新建立资料基线；首版没有 B→A 转发。
- 时间戳用于展示和审计，不单独作为跨中心因果顺序。修订保留明确前序关系；同一对象的分歧版本不能靠“最后收到者覆盖”消除。
- 两中心恢复、重新配对或重建索引时，区分来源身份和恢复代次，避免进度重置导致漏传或错误覆盖。

为控制复杂度，推荐“原发布方维护发布版本，接收方以带来源的新资料补充或派生”的模式。它比两中心任意改写同一共享记录容易解释和恢复；严格单向下不设计跨网共同编辑同一供应商主档的双向合并。

新增验收场景：链路中断期间两端独立使用；批次/分块重复发送不重复入库；乱序、缺包和附件缺失不产生不完整的可用资料；新协议版本拒收；超出重发窗口后基线恢复的实际覆盖范围；备份恢复后重放；跨网范围不夹带未发布数据；单向状态不冒充远端确认。当前均为设计要求，未实现或测试。首版不承诺基于远端确认的精确断点续传。

### 已确认的目录投递方式与候选导入流程

业务流为：用户明确发布 → 启用双网同步的 A 自动生成交换包 → A 指定投递目录 → 既有机制定期单向搬运文件 → B 内网指定接收目录 → 启用导入的 B 校验、去重、入库、建立索引 → 内网客户端检索和选择引用。

跨网搬运机制作为外部设施，本服务不负责建立跨网连接。A、B 使用同一 Rust 服务程序的不同配置，分别开启导出或导入任务；两端均可提供本网业务服务。具体目录、生成周期、扫描周期、重发周期、文件大小限制和保留期限作为配置，不在本轮硬编码数值。

### 双网同步配置与开关语义

启用开关与同步全量已发布资料是已确认要求。以下运行细节为建议，供后续规格确认：

- **配置内容：** 双网同步启用/关闭、实例职责（来源端导出或内网端导入）、对应目录与任务周期。首版每个实例只承担一个跨网方向的职责；B 不生成回传任务。关闭时不要求配置交换目录，普通单网中心仍可完整使用。
- **首次开启 A：** 建立初始投递任务，覆盖服务端当前保留的全部已发布资料与可用历史版本、撤回状态，再持续投递新增版本。初始集合使用明确快照边界，边界后的发布也必须进入后续任务，避免扫描和新增之间漏资料。删除或未保留的历史不能承诺补回。
- **关闭 A：** 停止启动新的导出任务，在明确的任务边界暂停在途工作，保留发布历史和生成进度。已放入投递目录的文件仍可能被外部搬运机制继续传输；关闭服务开关不能撤回这些文件，也不代表外部搬运已停止。界面应显示暂停生效状态。
- **重新开启 A：** 按持久生成进度补投关闭期间尚未打包的已发布版本；如果进度或保留范围不足，重新生成覆盖当前保留资料的基线。可重复生成和投递，B 按原始发布身份与版本去重。生成进度仅证明本地已生成交换包，不是 B 的接收进度。
- **关闭/开启 B：** 停止调度新导入；在途导入完成或回滚到可恢复边界后暂停。开启后重扫接收目录，按持久账本跳过已导入版本。关闭不删除现有资料、原始文件或账本；恢复只覆盖仍被保留的可用文件，不能找回已经被搬运系统清理的包。
- **范围与更新：** 一旦资料进入共享库，其发布版本自动纳入跨网投递，不再二次确认。用户在本地修改但尚未重新发布的内容仍是草稿；是否自动重新发布的产品规则保持待讨论，不能由同步开关隐式改变。

验收增加：关闭双网功能时正常使用单网中心；存量资料首次开启后被纳入投递；关闭期间继续发布、重启后开启能补投；反复开关不重复入库；A 开关关闭后外部工具继续搬运既有文件时状态不误报；B 暂停后恢复能重扫留存文件；切换过程中正在处理的任务不产生半成品可用资料。

### 交换包与接收处理

第一版建议以独立、不可变、可校验的交换包作为交付单位，扩展名暂记为 `.hubpkg`，容器格式待协议设计确定。包内含协议版本、包 ID、来源中心、发布对象与版本清单、必要关联快照及内容摘要；包含附件时也列入完整性清单。摘要用于校验内容完整性，不冒充来源身份验证。业务载荷与本地运行数据库解耦；一个包携带本批资料的完整发布快照，而不是依赖收齐所有前序补丁才能重建资料。

导出和导入分别承担以下职责：

1. **A 完成后投递。** 在投递目录之外、同一文件系统的工作目录构建并校验包，再原子改名放入投递目录。已投递的包不原地修改或覆盖；修订生成新发布版本。源目录原子可见不能保证搬运到 B 时也原子可见。
2. **B 按周期扫描。** 目录通知只可辅助唤醒，周期扫描负责补漏。文件存在、扩展名正确、文件大小暂时稳定都不能单独证明传输完成。B 将候选文件复制到自己管理的暂存区，验证完整结构、清单、条目摘要、格式兼容性和必要引用后再导入；不直接读取变化中的落地文件执行入库。
3. **未完成不入库。** 未传完或摘要不匹配的包延后重试，记录原因；持续失败在 B 显示待处理。文件内容变化后允许重新校验，不能因首次读取到半个文件就永久拒收。确定不兼容的协议或非法载荷停止自动重试，待升级或修正后处理。
4. **重复与乱序可处理。** 包 ID 和发布对象版本两层持久去重；同一包换文件名重投，或不同包包含相同资料，都不重复生成业务记录。相同身份不同内容报异常。较旧版本晚到可补充历史，但不覆盖当前较新版本；判断基于显式版本关系而非文件修改时间。
5. **导入可以恢复。** 完整包先保存到服务管理的持久存储，再事务提交本包发布记录和接收账本；中断后重扫重试。索引任务持久排队，失败后可重建。控制单包规模，避免超大事务；若必须拆包，采用明确的组清单和完整性门槛，不能把残缺组显示为完整资料集。
6. **接收目录保持简单。** 默认只读取搬运机制写入的目录。暂存、失败副本、归档和接收账本放在 B 自己管理的位置；不擅自移动或删除搬运工具的输入文件。是否清理接收目录由明确的运维约定决定。

恢复策略建议使用“新增/修订包定期投递＋保留窗口内重投＋周期性资料基线”。基线只覆盖声明的共享范围，并携带适用的撤回状态；不能因为某条资料没出现在一个包里就删除 B 中的记录。当前基线和完整历史归档仍是两种不同产物，保留策略分别定义。

A 在没有搬运工具可验证状态时，只显示“包已生成、已放入投递目录”，不直接标为“已发送”或“B 已接收”。B 显示“发现文件、待完整、校验失败、已入库、已可检索”。B 可以标出已收到清单揭示的缺项；完全未到达、又没有后续清单覆盖的包无法凭空被检测出来。按来源显示最近收到包的时间可以提醒检查，但不能据此断言具体丢了哪些数据。

为保持后台精简，目录交换先只提供配置、任务状态、失败原因、本地重试/重新导出和空间保留情况。供应商维护、报价参考和选型仍通过现有客户端使用中心资料。

新增验收例：复制到一半暂停；同一文件改名重投；旧包晚到；资料提交前后分别杀进程；索引任务失败后重启；相同版本不同内容；附件缺失；超大或非法包；重扫接收目录；接收端数据库从备份恢复后重新导入保留文件。需验证不重复、不半入库、不错误回退版本，且保留 B 自己的补充资料。

### 跨网机制的官方参考

[CouchDB 复制协议](https://docs.couchdb.org/en/stable/replication/protocol.html)以变更流、缺失版本查询、批次提交和检查点支持可恢复复制；这需要网络请求及响应，即使称为单向复制，也不等于支持严格无回程的物理单向通道。[持久复制任务](https://docs.couchdb.org/en/stable/replication/replicator.html)展示任务状态与重试机制；[冲突模型](https://docs.couchdb.org/en/stable/replication/conflicts.html)明确实际合并属于应用业务逻辑，且版本树不等于永久业务归档。本项目借鉴持久进度、幂等和业务冲突分离的原则，不据此采用 CouchDB 或宣称其协议可直接用于双网部署。检索日期为 2026-09-29，所读 stable 文档标为 3.5，复制协议标为版本 3。

## 三种候选定位

1. **推荐：公司共享资料库与交换中心。** 本地保持工作空间；主动发布；中心保存可追溯版本，提供检索与分发；接收方预览并纳入本地。价值与维护成本较均衡。
2. **轻量文件中转站。** 上下载交换文件、保留历史版本。最小，但难以按供应商、条件和项目检索，容易只比共享文件夹多一个入口。
3. **中心业务平台。** 中心承担在线编辑、审批、采购流程等。能力更多，但会增加双端业务规则、离线一致性和后台维护负担，暂不建议。

## 推荐的第一版闭环

同事 A 在本地完成一次询价，选择发布记录。系统列出将包含的供应商、物料、询价条件和项目来源；用户确认范围。中心接收后保存不可变发布版本，返回持久回执，随后完成索引。同事 B 搜索资料，看到价格条件、时间、来源、版本及共享者标识，选择纳入自己的本地库或项目，保留来源引用。

核心功能建议限制为五组：

1. **发布与接收：** 明确选择对象、关联资料预览、重复提交幂等、失败重试、接收回执。上传中、已持久保存、已可检索、已纳入本地分别显示。
2. **公司资料检索：** 供应商、物料和历史询价，支持规格、时间、地区和项目等已具备字段；无法同口径比较的报价明确标识。完整统计分析延后。
3. **项目成果复用：** 发布项目成果快照与其报价依据；新项目选择性引用或复制，保留来源版本。中心后续更新不改写已经采用的历史成本快照。
4. **来源与版本：** 发布者/设备、来源对象 ID、发布批次和版本、业务发生时间与服务端接收时间分开保存；新版本替代旧版本，但旧成果可追溯。疑似重复供应商先提示，不凭名称自动归并。
5. **可恢复存储和轻量运维：** 查看发布失败、待索引、冲突、空间与备份恢复状态；有可验证的备份及恢复步骤。完整设备备份是独立功能，不能把共享库当成各设备全量备份。

接收端必须在资料纳入前校验必需引用。引用闭包不等于整库打包：报价需要相关物料与供应商，但不能顺带发布无关联系人、其他项目或全部历史日志。必要时使用独立来源描述与发布快照，避免暴露未选择的项目内容。字段日志可能包含旧值，也要遵守发布范围。

发布后的本地编辑先留在本地；是否自动产生新发布版本尚未确认，暂以显式再发布作为讨论起点。中心撤回记录只影响后续发现和获取，不能承诺擦除同事已经导出的本地副本。设备本地删除不应自动删除公司已发布成果。

## 保持中心轻量的技术方向

建议先采用单个 Rust 服务、清晰的领域模块、一个持久数据库和必要的文件存储。模块可围绕发布、资料索引、分发、运维划分；不提前拆微服务，不默认加入 Redis、Kafka、搜索集群或 Kubernetes。

[Axum 官方文档](https://docs.rs/axum/latest/axum/)说明它复用 Tokio/Tower 生态，可作为后续 HTTP 层候选；尚未做框架对比与版本锁定。按 Rust Patterns 采用明确的 ID 类型、发布状态枚举、结构化错误和有界并发。按 Backend Patterns 保持事务、分页、集中错误处理和可观测性；不照搬其中 Node 技术栈或进程内队列示例作为可靠任务存储。

数据库先保留一个决定点：单实例、受控写入量可评估服务端独占的 SQLite；需要较高并发写入、多实例或已有数据库运维能力时评估 PostgreSQL。[SQLite 官方说明](https://www.sqlite.org/whentouse.html)明确单库同时只能有一个写者。不能让多个客户端通过共享目录直接打开中心数据库文件。规模未知时，不给出未经测试的容量承诺，也不承诺首版同时支持两套数据库。

中心首先实现发布协议与只读检索，尽量不复制 Dart 的项目计价、选型、AI 解析等业务引擎。可复用现有 ID、引用校验、删除与恢复语义作为兼容要求，但新发布快照和旧全库交换必须区分协议。后续以 Dart/Rust 共享测试样例验证金额、时间、空值、枚举、版本以及未知字段行为。

## 中心边界与稳定性要求

结合 Codex Security 的边界分析思路，本节是待验证设计要求，未执行安全扫描，也没有确认漏洞：

- 公司成员接入和发布来源需要可识别；按公司单空间设计，先讨论简单设备配对/凭据，复杂账号权限平台不列为首版默认功能。服务端不能把客户端声明的发布者直接当成已验证身份。
- 发布对象大小、条目数、嵌套与关联展开需要限额；网络输入先解析成合法类型，避免任意文件路径和无限资源占用。
- 数据持久保存后才能返回成功回执；索引失败可重建和重试，不应丢失已经接收的原始发布版本。
- 如果有附件，明确附件校验、就绪状态和数据库记录的一致性；不将未保存完整的附件标成可下载。
- 备份、撤回、恢复和删除分别定义，保留恢复点；连接凭据和本地 AI 密钥不进入发布载荷。

## 后续设计的验收问题

中心关闭时，客户端原有业务是否完整可用？重复发布和响应丢失是否产生重复资料？发布后崩溃能否恢复回执和索引？所选报价的引用是否完整且没有夹带其他项目？历史成果是否保持当时采用的报价快照？撤回、删除和旧设备重新连接是否造成错误复活？新旧协议不兼容是否在修改本地数据前明确拒绝？中心备份是否经过实际恢复验证？

这些成为开发与后续验收的输入。首批 Rust 工程位于 `services/supplier_hub`，启动与能力边界见该目录 README；未推送或合并分支。
